## trend_bot 치명적 버그 발견

### 문제
Nado API 최소 주문 크기 = **$100 notional** (notional = BTC수량 × 가격)

```
ORDER_USD = $75 → 0.001 BTC
0.001 × $73,500 = $73.5 < $100 → API error 2094!
```

### 더 심각한 문제: 에러를 성공으로 인식

```python
# Before: "error" 상태를 성공으로 오인
return result.get("status") != "failure"
# API는 "error"를 반환하는데 "failure"만 체크함

# After: 둘 다 체크
return result.get("status") not in ("failure", "error")
```

결과적으로 trend_bot은 **오랫동안 가상 트레이딩**을 하고 있었음.
주문은 실패하지만 state는 업데이트 → 거래소 실제 포지션 ≠ state

### 수정 사항

```python
# ORDER_USD 변경
ORDER_USD = 75.0   →   ORDER_USD = 150.0
# 150 / 73,500 = 0.00204 → 0.002 BTC
# 0.002 × $73,500 = $147 > $100 ✓
```

## arc_farmer Faucet 스킵 로직

### 기존 문제
계정마다 Faucet 시도 → 실패 → **30분 대기** → 다음 계정
하루 20개 처리하면 6~10시간 소요 (30분 × 20 = 600분)

### 해결
```python
def run_faucet_for_account(...) -> str:
    # "success" | "skipped" | "failed" 반환

faucet_result = run_faucet_for_account(account, state, dry_run, faucet_counter)
if faucet_result == "failed":
    print(f"  → Faucet 실패, 가스비 없음 — 계정 스킵")
    return [{"action": "faucet_skip", "status": "skipped"}]
```

Faucet 성공할 때만 카운터 증가 → 연속 실패 계정들은 30분 대기 없이 통과.

## 배운 것

- 에러 코드와 에러 상태는 다르다. "failure" vs "error"가 다를 수 있다.
- 봇이 조용히 돌아가고 있다고 해서 제대로 작동하는 게 아님. 로그 필수.
- 병목 찾기: 30분 × N이 어디서 발생하는지 찾으면 10배 빨라진다.
- 최소 주문 크기 = 절대 하드코딩하면 안 됨, API 문서 재확인 필수.
